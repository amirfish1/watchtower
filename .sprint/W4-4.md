# Lane W4-4 — Stop WatchTower exhausting the GitHub GraphQL quota

Status: in progress (2026-09-03)

## Measured evidence (2026-09-03, amirfish1/BYM-Finie)

1. **`gh api rate_limit` lies about GraphQL.** REST `rate_limit` reported
   `graphql: used=0 remaining=5000` while the authoritative in-band block
   `gh api graphql -f query='{rateLimit{used remaining}}'` reported
   `used=1025 remaining=3975` at the same moment.
   => `_graphql_rate_limit_remaining()` (REST) can never trip its
   `_GH_GRAPHQL_LOW_THRESHOLD` guard. This is the root cause the previous
   tickets (OPS-589, WATCHTOWER-19) mis-attributed to an "invisible
   user-level aggregate limit".

2. **Background burn ~4,680 pts/hr** against the 5,000/hr quota: authoritative
   `used` moved +26 in a 20s idle window with the daemon and Becky lanes
   running and no command of ours in flight.

3. **`body` is free.** `issues(first:100)` costs exactly 1 point with body and
   1 point without it — GraphQL cost is node-count based, not field based.
   Dropping `body` from the list query saves 0 quota; done naively it *breaks*
   status/eligibility, because the `<!-- watchtower -->` metadata block
   (claimed_by, priority, readiness, needs_input, history, resolution) lives
   in the issue body. Handled with a body cache instead (see below).

4. `--limit` is the real per-call lever: 1 pt per 100 nodes, so 1000 -> 200
   cuts a full page-set from ~10 pts to ~2 pts.

## Plan
- A. Authoritative quota reader (in-band graphql rateLimit) so the pre-emptive guard works.
- B. Per-poll quota logging to ~/.watchtower/gh-quota.log.
- C. Poll-in-flight lock + configurable TTL; wt status/ls/claim serve cache.
- D. --limit 200, `updated:>=` window for closed.
- E. Lazy body via persisted body cache (keyed number@updatedAt).

## Progress 2026-09-03 20:30

Committed 74e833d (meter + TTL gate + limit 200 + quota log + tests).

Live verification after `launchctl kickstart -k gui/$UID/ai.watchtower.watcher`
showed a **residual hole the TTL gate did not close**: on amirfish1/BYM-Finie,
6 reader fetches to 0 poller fetches in one 90s window. Cause: live workers
write continuously, every write calls `_invalidate_list_cache` which marks the
*shared* snapshot stale, and every reader read that as "go live". Only the
process that actually wrote needs a live read.

Fix (patch 7/8): split staleness into `stale_local` (this process wrote --
never coalesced) and the persisted `stale` flag (someone else wrote -- readers
coalesce behind whichever refresh is already in flight). Readers that do go
live now publish the poll marker for the duration of their fetch, so N
concurrent lanes collapse to one list.

Baseline measured before the change: **75 pts / 60s = ~4,500 pts/hr** against
the 5,000/hr quota.

## The finding that matters most, and what it does NOT fix

`gh api rate_limit` reports a GraphQL bucket that is not this token's GraphQL
quota. Every quota guard in this module read it, so it could never trip. Fixed.

But the account-wide burn is **not** WatchTower's. With
`ai.watchtower.watcher` fully booted out, the authoritative `used` still
climbed ~27-32 pts per 30s (~3,500 pts/hr) against the 5,000/hr quota, and a
process sample over that window found almost no `gh` invocations on this
machine. Something else on this GitHub account is the dominant consumer.
Filed **OPS-929**. This lane's changes cut WatchTower's own contribution and
make the burn measurable (`~/.watchtower/gh-quota.log`); they cannot reach a
consumer that is not WatchTower.
